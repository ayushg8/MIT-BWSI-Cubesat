1Overview

The software runs a five-state loop that the operator steps through. It captures only when the spacecraft is pointed at the ground and holding still, scores each frame on board, and downlinks the best frames first over a link slow enough that choosing is mandatory.

Table 1. Design numbers from config.py
Flight states5BOOT, WAITING, IMAGING, IDLE, DOWNLINK; SAFE MODE sits outside the loop
Link rate1,200 B/smatches a 9600 baud radio
Pass budget72,000 Bone 60 s downlink window
Captures accepted10 / 16at 640 × 480, scored by the repo's own gate

2.3Imaging gate

Two conditions, both required. Nadir lock engages under 45° and holds until the angle passes 55°, so the camera does not flicker at the boundary. The gyro rate must stay under 1.0 rad/s.

2.4Downlink

The link is throttled to 1,200 B/s, so a 60 s window carries at most 72,000 B. The queue sends P1, then P2, then P3, and stops at the first image that does not fit. The real code sleeps one second per chunk; this plays it back faster. The queue is the six best accepted captures with their real 640 × 480 JPEG sizes, ranked by combined score. The P1/P2/P3 labels are illustrative: real tiers need a live coverage grid.

4Limits

Table 3. Known limitations
Blur threshold20.0 is an uncalibrated placeholder, flagged as such in config.py. Laplacian variance depends on image resolution, so the right value has to be set against the real imaging surface.
No yawThe IMU has no magnetometer. The software tracks pitch and roll for nadir pointing but not yaw.
Wi-Fi, not UHFWi-Fi stands in for a flight radio. The 1,200 B/s throttle reproduces the rate of a 9600 baud link.
Offline analysisTerrain segmentation and route planning exist in the repo and run in tests. They are not wired into the flight loop.
